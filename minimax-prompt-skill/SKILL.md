# MiniMax Prompt 优化 Agent Skill

## 概述

本 skill 帮助你在向 MiniMax 2.7 提交 prompt 之前对其进行优化。支持从零创建和优化已有 prompt 两种模式。

**核心原则：中文优先** — 整个交互过程中使用中文引导，优化后的 prompt 中建议使用中文引导说明（MiniMax 2.7 对中文优化更佳）。

**适用平台：** Claude Code（`/minimax-prompt`）、Copilot CLI（`skill minimax-prompt`）、Gemini CLI（`activate_skill minimax-prompt`）、OpenCode（`/minimax-prompt`）

> 本 skill 核心规则平台无关，各平台通过自己的 skill 加载机制引用同一套规则。详见 `references/` 目录下的平台适配说明。

## 工作流程

### 流程概述

交互入口后，按以下三阶段执行：

```
阶段 1: 上下文收集   →   阶段 2: 优化   →   阶段 3: 编辑确认
```

各阶段简要说明（详见后续章节）：

- **阶段 1 · 上下文收集** — 收集任务类型、目标语言、原始 prompt、约束条件和参考信息
- **阶段 2 · 优化** — 基于 MiniMax 2.7 规则体系对 prompt 进行优化，生成改动说明
- **阶段 3 · 编辑确认** — 展示优化前后对比，提供确认/编辑/回退/取消选项

### 阶段 1: 上下文收集

依次收集以下信息（按需提问，一次一问）：

1. **任务类型** — "你想做什么？A) 生成新代码 B) 调试 C) 重构 D) 代码审查 E) 编写测试 F) 文档 G) 通用"
2. **目标语言/框架** — "使用什么语言或框架？"（自动匹配优化规则）
3. **原始 prompt 或需求描述** — "请提供你的原始 prompt，或描述你的需求"
4. **特殊约束** — "有什么特殊要求？如输出格式、性能要求、安全要求等"
5. **参考信息** — "有什么参考代码、API 文档或错误信息要补充？"

> 如果调用时已附带需求描述（快速模式），跳过步骤 1-2，直接从步骤 3 开始。

### 阶段 2: 优化

基于收集到的上下文，应用 MiniMax 2.7 优化规则生成优化版 prompt。同时生成改动说明（2-3 条主要优化点，说明优化了哪些方面以及为什么）。

### 阶段 3: 编辑与确认

展示优化结果，按以下模板呈现，引导用户选择操作：

展示模板：

```
🔍 优化完成

改动说明：
  • （主要优化点 1）
  • （主要优化点 2）
  • （主要优化点 3）

── 优化版 Prompt ──
[完整优化后的 prompt]

── 原版 Prompt ──
[仅优化模式显示]

操作选项：
  [确认] → 输出最终 prompt，继续后续任务
  [编辑] → 用户自行修改 prompt
  [回退] → 使用原始 prompt
  [取消] → 退出 skill
```

用户输入对应关键词即可操作。

## 调用方式

### 交互模式
直接调用 skill（不带参数），进入逐步交互流程。skill 会依次询问任务类型、目标语言、原始 prompt、约束条件等，收集完整上下文后再进行优化。

### 快速模式
调用时附带需求描述，跳过任务类型和目标语言的询问步骤，直接进入原始 prompt 收集和优化阶段。例如：`/minimax-prompt 帮我优化一个 ArkTS 组件`

## MiniMax 2.7 优化规则

### 1. 角色与任务明确化

- 为 prompt 添加与任务相关的角色设定（如"你是一位资深 Python 后端工程师"，MiniMax 2.7 对精准角色定义响应更佳）
- 将模糊需求转化为结构化任务描述

### 2. 指令结构化

- 使用编号列表或分节方式组织复杂指令
- 关键约束前置（语言、框架、风格、禁止项）
- 显式声明输出格式（纯代码 / 代码+说明 / Markdown / JSON）

### 3. 上下文边界管理

- 控制 prompt 在 MiniMax 2.7 的有效窗口内
- 对过长的原始 prompt 做摘要压缩
- 仅提供相关代码片段，而非整个文件

### 4. 少样本示例（Few-shot）

- 对复杂代码任务添加 1-2 个输入/输出示例
- 示例风格与期望输出一致
- 示例放在指令之后、问题之前（MiniMax 2.7 特定偏好）

### 5. 输出约束

- 要求输出可执行代码（而非伪代码）
- 包含必要的 import/依赖声明
- 添加关键注释，注释语言与用户指定的自然语言保持一致（如用户用中文描述需求则注释用中文）
- 指定错误处理和边界情况要求

### 6. 代码生成场景规则

| 子场景 | 优化策略 |
| --- | --- |
| 生成新代码 | 明确功能描述 + 输入/输出定义 + 依赖约束 |
| 调试 | 完整错误信息 + 期望行为 + 最小复现 |
| 代码审查 | 定义审查维度（正确性/性能/可读性/安全） |
| 重构 | 原代码问题 + 目标架构/模式 |
| 测试编写 | 测试框架 + 覆盖率目标 + mock 策略 |
| API 集成 | API 文档片段 + 认证方式 + 期望响应 |

### 7. 中文优先原则

- skill 与用户的全部交互使用中文（包括引导语、提示、选项说明）
- 优化 prompt 时，建议用户在 prompt 中使用中文引导说明（MiniMax 2.7 对中文优化更好）
- 代码注释保持用户习惯的语言
- 改动说明使用中文展示

### 8. ArkTS / 鸿蒙专项规则

| 子场景 | 优化策略 |
| --- | --- |
| ArkTS 代码生成 | 明确声明 `@Entry`/`@Component` 装饰器，指定 UI 组件树结构，注明状态管理方式（`@State`/`@Prop`/`@Link`/`@Provide`/`@Consume`） |
| 页面/路由 | 指定路由配置方式（`router`/`Navigation`），说明页面间参数传递模式 |
| 数据管理 | 明确数据模型定义，指定本地存储（`@StorageLink`/`PersistentStorage`）或远程数据获取方式 |
| 设备能力调用 | 注明需要调用的系统能力 API 模块（传感器/蓝牙/网络/相机等），自动补充权限声明要求 |
| UI 组件 | 指定使用 ArkUI 原生组件（`Column`/`Row`/`List`/`Grid`/`Scroll` 等），明确布局方式（Flex/线性/层叠） |
| 性能约束 | 避免 `any` 类型，使用显式类型标注；避免在 `build()` 中进行耗时操作；合理使用 `LazyForEach` 处理长列表 |
| 跨端兼容 | 如需要，说明适配的设备类型（手机/平板/折叠屏/智能穿戴），要求使用响应式布局 API |

**ArkTS 语言注意点：**

- 强制类型系统 — prompt 应要求产出类型安全的代码，禁止 `any`（除非系统 API 返回）
- 装饰器语法 — `@Component`、`@State`、`@Builder` 等装饰器必须正确使用
- 不支持的 JS 特性 — `in` 操作符、`with` 语句、部分动态特性不可用
- 并发模型 — 使用 `TaskPool`/`Worker` 而非传统多线程
- API 版本 — prompt 中应指明 API 版本（如 API 12+），避免使用废弃 API

> **注意：** 规则体系设计为可扩展架构，后续可追加新的场景规则，无需重构整体结构。

## 退出协议

- `回退` / `revert` — 恢复原始 prompt，退出 skill
- `取消` / `cancel` — 退出 skill，不输出任何内容
- 编辑后内容为空 — 提示"内容不可为空"，提供重新编辑或回退
- 中断 — 用户中途中断交互，输出当前最新版本后退出

## 边界情况处理

| 场景 | 处理方式 |
| --- | --- |
| 原始 prompt 为空 | 进入创建模式，引导用户描述需求 |
| 编辑后内容为空 | 提示不可为空，提供重新编辑或回退 |
| 多次编辑/回退 | 仅保留原始版和最新编辑版，不保留中间历史 |
| 非代码场景 | 使用通用规则，跳过代码/ArkTS 专项规则 |
| 对话上下文过大 | 提示用户当前情况，建议手动清理 |
| 中途中断 | 输出当前最新版 prompt 后退出 |
